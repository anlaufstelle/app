# Security notes — key rotation and authentication hardening

This excerpt translates the operational rotation guidance and its idempotency consequence in the [German security notes](../security-notes.md).

Prepend the new primary key to `ENCRYPTION_KEYS` and retain old keys initially. One ring serves the entire installation, not each facility. `reencrypt_fields` rewraps database fields including TOTP secrets; `reencrypt_files` streams referenced attachment chunks through encrypted staging and atomic replacement. Unfiltered `reencrypt_files --verify` reads every referenced version with the primary key alone, including format-dependent chunk binding. Remove old keys only after field rotation without warnings, full verification, resolving ImportJob temporary files and staging remnants without database rows, and actual expiry of affected local/off-site backups. Recreate processes with the shortened ring and verify again without filtering. Retained older backups require their historical keys in separate escrow. The manifest records progress, not integrity; a kill can prevent the audit summary. For roles, interruption/concurrency behaviour and acceptance follow [Ops Runbook § 9.5](ops-runbook.md#file-rotation-and-old-key-removal).

Old idempotency fingerprints cannot be rewrapped because the original request payload is no longer available. Removing their key disables payload collision comparison for those events, while duplicate detection remains. This documented loss of functionality is no additional reason to retain the key and is not a data-subject protection goal. Legacy bare SHA-256 values and fingerprints whose key is absent have no comparison basis and are treated as duplicate matches without payload comparison. Concurrent MFA verification preserves rewrapped TOTP secrets; repeat `reencrypt_fields` if it reports devices left under the old key after retries.

## Authentication, release metadata and guard coverage

Ten backup codes carry 128 bits each and are stored as purpose-separated 96-bit HMAC prefixes derived from `SECRET_KEY`. Earlier SHA digests and the old input format are invalid; rotating `SECRET_KEY` also invalidates codes. Anonymous recovery uses 5/min per IP and 10/h per normalized username without increasing device throttling. Authenticated device throttling and atomic single use remain. `MFA_ENABLED` and `MFA_DISABLED` record completed session revocation as `sessions_revoked: true`, without claiming a counted number of sessions. The [user guide](user-guide.md#two-factor-authentication-2fa) explains **Neues Gerät einrichten** (set up a new device): existing verified MFA plus sudo; only acknowledgement of new codes replaces confirmed TOTP devices, while passkeys remain. Device change and voluntary deactivation revoke all other signed-in sessions of this account without a session scan; they are signed out on their next request. The initiating session stays signed in and receives a new session ID. The factor change, revocation and audit are committed together; on failure the previous factor remains valid and confirmation can be retried. The password stays valid; previously issued password-reset and invitation links may become invalid because of the hash change. The offline salt is unchanged. Offline devices without a connection cannot be remotely erased; on reconnection the existing revocation check requires signing in again and holds pending transmissions. Without a usable second factor, the admin reset remains the fallback.

Passkey completion is limited to 60/h per user before JSON parsing. Cryptographic failures and malformed completion requests received during a started verification count; an interrupted started verification consumes the challenge and records `WEBAUTHN_FAILED` with fixed event/error codes, without setting MFA/OTP markers. A local browser cancellation without a completion request is not observable by the server.

Recipient/purpose metadata accepts at most 200 characters and rejects detected email/phone patterns and typical name pairs before release with HTTP 400, without reflecting rejected values. Institutional prefixes such as “Stadt Musterstadt” remain allowed. This heuristic does not guarantee PII-free values; accepted text remains in the immutable audit log. Production defaults `DJANGO_AUDIT_DETAIL_STRICT=true`; an explicit `false` changes unknown-key handling but never disables this value validation.

The endpoint guard recursively walks the active URL resolver at runtime for POST, PUT, PATCH and DELETE, including admin/WebAuthn routes, inherited handlers, form views and functions using `require_POST`/`require_http_methods`. It recognizes common declaration forms (inherited handlers, form views, method filters and project limit wrappers), applying fail-closed checks within those forms. It resolves effective class, handler and method-filter bindings and known Django dispatch forwarding through the MRO and the method-preserving demo gate. Limits require verifiable evidence from `core.utils.ratelimit`, a concrete finite rate, matching method and `block=True`; copied attributes and skipped parent dispatches provide no proof. Within recognized declaration forms, custom dispatches, instance bindings and dynamic rates without a proven outer limit or method filter fail. Exceptions check the URL name, POST method and known target class or function: `logout` (`CustomLogoutView.post`, session termination including quick exit), `admin:logout` (`AdminSite.logout`, admin session termination) and `core:client_rename_warning` (`ClientRenameWarningView.post`, a read-only warning outside the update quota). Undetected cases include custom auth-mixin check hooks (`LoginRequiredMixin`, `PermissionRequiredMixin`, `UserPassesTestMixin`) before throttling and dispatches replaced via `as_view(...)` under the URL name `logout`; the class exception does not prove the dispatch actually executed there. This provides limited evidence for imported bindings and configured limits, not load capacity, GET-handler semantics or later binding changes. Configuration POSTs and password changes use 60/h per user; existing custom-dispatch limits run before dispatch processing. Anonymous password/invitation setup uses 5/min per IP, language selection 60/h per user or IP. Login, password and recovery forms share mutation budgets. Both passkey begin paths use 60/h before parsing (registration per user, authentication per user or IP). Admin routes use 60/h per URL and user or IP; admin login shares 5/min per IP and 10/h per normalized username across mutations. Caddy has no edge rate limit; excess requests receive HTTP 429. Markup guards include installed Django-admin/Unfold templates with specific justified exceptions; the CSRF guard also scans package Python. The inline/Alpine guard remains limited to project templates.

## Branch protection and maintainer evidence

Branch protection/rulesets are unavailable for the private development repository without GitHub Pro; the substitutes are local gates, signed tags and the release dry run. For the public app repository, a ruleset is planned: no force pushes and no branch deletion. Evidence of active settings is provided through the maintainer checklist #1597. The local source tree does not prove active GitHub settings; this excerpt makes no claim that the ruleset has been checked.

Two separate rulesets are planned for `refs/heads/main`: `main-integrity` blocks force pushes and deletions without bypass actors; `main-pr` requires pull requests and status checks, with an “Always” bypass only for the named release identity and no restrict-updates rule; check names must be compared with an app run before configuration.

## Limits of free-text review (#918)

Online review is an organisational aid for the four fixed long-text fields and configured unencrypted event text/textarea values. It does not extend read permissions, decrypt values or encrypt existing data. Pseudonyms, titles, dynamic person/case fields and the derived search index are outside this list. Local phone/email/date/address heuristics can produce false positives or miss sensitive content; neither the absence of a match nor a review mark guarantees GDPR compliance.

Marks contain no source text: only target, field, date, account, timestamp and a purpose-separated HMAC bound to content and target. Validity is checked against current content and date; changing `SECRET_KEY` invalidates earlier HMACs. Restoring exactly the previous text produces the same content fingerprint. This does not prove a complete modification history. RLS isolates facilities' metadata rather than encrypting source text. Marking and revocation log neither text values nor matched snippets. Displaying notes of a person with additional details writes the same read entry as the person detail page (once per displayed person, without text); other target types keep the existing behaviour of their detail pages. Suggestions about contact creation, sensitivity and neutralisation do not change data themselves. Review responses carry `no-store`; no separate offline review data store is created.
