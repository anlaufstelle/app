# Disaster recovery — key rotation and escrow

This excerpt translates the key rotation requirements in the [German recovery guide](../disaster-recovery.md#4-schlüssel--und-secret-wiederbeschaffung).

An older backup set can contain database fields and attachments encrypted under several key generations. Restore requires every key used in that set in `ENCRYPTION_KEYS`, even after the live data has been fully rotated using `reencrypt_fields` and `reencrypt_files`. Rotation does not change existing backups. Keep the key history in escrow separately from backups until the last affected local or off-site set actually expires; longer retention requires longer key retention. A restore using only today's primary key can otherwise leave contents unreadable. Follow [Ops Runbook § 9.5](ops-runbook.md#file-rotation-and-old-key-removal), including its import/staging limits, before removing keys from the active ring. Backup encryption uses the separate `BACKUP_ENCRYPTION_KEY`; successful backup HMAC verification does not prove inner field or attachment decryption.

## Audit anchor and media verification

The audit high-water mark uses `DJANGO_AUDIT_HWM_PATH` or the Compose default `/data/audit_hwm.json`, including when the variable is empty or absent. It lives on the separate `audit-anchor` volume. Maintenance services write it; `web` has read access. Initialize the signed anchor before the first backup and preserve the original `DJANGO_AUDIT_HASH_KEY` for recovery. Follow [Ops Runbook § 6.7](ops-runbook.md#67-back-up-and-verify-the-audit-high-water-mark-refs-2022) for volume permissions, migration of an existing anchor and the limitation that this does not protect against the host or owner.

Current `backup.sh` aborts with exit code 1 before publishing a set if the anchor is missing, empty or unreadable. Older sets may lack `audit_hwm-<timestamp>.json`; restoring one is incomplete, and the anchor verification step cannot run. Check the set first and choose an older complete set if necessary.

`restore.sh` uses the configured anchor path or the default and aborts before changes if the set lacks the anchor copy. Restoration still requires confirmation (`--yes` or `RESTORE_CONFIRM=ja`). On a host without a custom anchor path, the explicit `--skip-audit-anchor` option restores without checking or importing the anchor; subsequent anchor verification cannot run. If `DJANGO_AUDIT_HWM_PATH` is set, the option does not bypass checking or importing that anchor. The production recovery drill uses the default even without a custom path: a missing or invalid copy produces `FAIL`, exit code 1 and no compliance evidence. The development backup format has no anchor and remains a drill with gaps (exit code 2). Record the source and reconstructed environment's actual anchor paths, whether custom or default, in the drill report.

Media archive verification runs in one disposable maintenance container while `web` and `cron` remain stopped. Its temporary working directory is on the persistent `/media` volume, outside `MEDIA_ROOT`, and is removed afterwards. The German guide's verification command uses `/media/media-verify-$RESTORE_TIMESTAMP` and `${MEDIA_ROOT_CONTAINER:-/media/media}`. Compare SHA-256 and size of the encrypted files with the authenticated archive; original filenames and plaintext sizes require the separate download check. See the [German recovery steps](../disaster-recovery.md#schritt-4--db-backup-entschlüsseln--wiederherstellen) for the complete procedure.

## Resuming an interrupted activation

Restore preflight, extraction and attachment checks use disposable `maintenance` containers and work while `web` is stopped. The German recovery command no longer starts `web` before restore. Existing databases are preserved as `<POSTGRES_DB>_vor_restore_<timestamp>_<PID>`. What remains after an interrupted restore depends on the phase; first read the actual state from the existing database names (`\l` in `psql`).

1. **After the recovery database was created, before the switch begins** (import, manifest comparison, media staging, attachment path check, stopping the services): an error or a catchable signal (Ctrl-C, `kill`) drops `<POSTGRES_DB>_restore_<PID>` and the staging directory, and the target stays unchanged. After a hard abort (`kill -9`, power loss, host reboot) the cleanup does not run: the database stays behind, possibly incomplete but never active, and so may a staging directory `<MEDIA_ROOT_CONTAINER>.restore.<PID>`. The target is unchanged and the leftover can be dropped safely with `DROP DATABASE "<POSTGRES_DB>_restore_<PID>";` after acceptance. The repeat run creates a new one under its own PID.
2. **During the switch** (between the two renames): on an error or catchable signal the script deliberately keeps the already verified `<POSTGRES_DB>_restore_<PID>`, restores the previous state under the target name and prints the `ALTER DATABASE` commands that apply; if the second rename fails it renames the previous database back itself. After a hard abort the target name can be missing for a moment: the previous state is then `<POSTGRES_DB>_vor_restore_<timestamp>_<PID>` and the verified state is `<POSTGRES_DB>_restore_<PID>`. **Do not drop either.** Repeat the same restore command with `--yes` and the same signed archives; do not start `web` or `cron`. The run detects the missing target and activates a newly built, verified state.
3. **After the second rename:** no `<POSTGRES_DB>_restore_<PID>` exists any more; the backup state is active under the target name and the previous one is `<POSTGRES_DB>_vor_restore_<timestamp>_<PID>`. If anchor installation or media activation fails afterwards, the cleanup reports the resumable state instead of dropping a database; continue as described below. A hard abort in this phase leaves the same state, only without the message.

The preserved previous database is never dropped automatically; remove it with `DROP DATABASE` after acceptance.

If anchor installation or media activation fails after the database switch, the database already contains the backup, while media and the anchor may still differ. The error reports the reached `phase`, active and previous database, media, staging, previous media path, anchor and signed set. Validated media staging remains available. Keep `web` and `cron` stopped, fix the cause, and repeat `sudo ./scripts/ops/restore.sh --yes` with the same signed DB and media archives. Do not start `web` first. The repeat builds a new verified database and staging directory, installs the anchor again and activates media through maintenance containers. Further preserved databases may result. Start writers only after the final success line and the checks in steps 4b/5 and section 7; clean up leftover staging and preserved databases afterwards using the logged paths. This is a recovery path, not a shared transaction across PostgreSQL, media and the anchor. If media rollback itself fails, inspect both reported media paths manually.
