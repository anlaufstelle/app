# Threat model — TB5 key rotation

This excerpt translates the key rotation assessment in [TB5 of the German threat model](../threat-model.md#tb5--off-site-backups).

`ENCRYPTION_KEYS` is one ring for the entire installation, with no facility keys. `reencrypt_fields` rotates database fields; `reencrypt_files` rotates referenced attachments. Unfiltered `--verify` authenticates every referenced version with the primary key alone. Rotation does not change older backup sets: a compromised old key can still decrypt their old inner ciphertext if the attacker also obtains the decrypted backup contents. Local/off-site retention and separate key escrow remain organisational prerequisites for key removal; unlimited off-site retention provides no proven finite removal date. ImportJob temporary files and staging remnants without database rows are outside attachment verification. Follow [Ops Runbook § 9.5](ops-runbook.md#file-rotation-and-old-key-removal).


## Offline key lifetime and revocation check

**Offline key and revocation check** (#2528). The non-extractable `CryptoKey` derived from the password and server salt remains stored in browser IndexedDB across tab, browser and device restarts. “Non-extractable” prevents export through WebCrypto; protecting the stored key against access to the browser profile depends on **device encryption and screen locking**, which are mandatory for offline devices. Derivation freezes an absolute deadline using the facility's `session_absolute_hours` (default 12 hours). Activity and navigation never extend it. The app checks on load, before decryption/storage/replay, on tab return and every 60 seconds. At expiry it removes the key and displays “Offline key expired — please sign in online”; unsent work stays encrypted and becomes readable after another online sign-in with the same password and salt. The idle window still applies separately. Missing or invalid expiry metadata blocks access; bundles without valid `expiresAt` are expired. An observed backwards device clock locks the key, but clock manipulation remains a residual risk. A powered-off app cannot remotely delete the key.

An HTTP/network/processing error fetching revocations (including 500/429), or an invalid response structure, pauses queue and edit replay: “Synchronization is waiting for the revocation check”. The blocking state is stored in local IndexedDB. Each replay run also requires its own fresh, structurally valid, successfully applied and persisted revocation check; an earlier approval never authorizes a later run or another tab, even when metadata writes and fallback deletion both fail. Missing or unreadable metadata blocks replay; recovery from a read failure also requires another successful check. The next sync sequence checks again, as does a direct save from the offline client record. A failed check preserves unsent work in encrypted form. Existing idempotency keys remain intact, and the server gates (422 for revoked people, 409 for status conflicts) remain authoritative. Device encryption does not replace these server checks.

## Authentication and application limits

Backup codes are purpose-separated 96-bit HMAC prefixes derived from `SECRET_KEY`, with 128-bit random input. Database digests alone provide no offline verification oracle without the server key. Earlier codes and codes issued before a `SECRET_KEY` change are invalid. Anonymous recovery limits are 5/min per IP and 10/h per normalized username without increasing the victim device throttle. A local passkey cancellation without a server completion request remains unobservable.

The endpoint guard recursively walks the active URL resolver at runtime for POST, PUT, PATCH and DELETE, including admin/WebAuthn routes, inherited handlers, form views and functions using `require_POST`/`require_http_methods`. It recognizes common declaration forms (inherited handlers, form views, method filters and project limit wrappers), applying fail-closed checks within those forms. Only effective handler/dispatch bindings with verifiable evidence from `core.utils.ratelimit`, a finite matching blocking limit (`block=True`), or a proven method filter pass. Within recognized declaration forms, shadowed parent dispatches, copied attributes, custom dispatches/instance bindings and dynamic rates without a proven outer limit or method filter fail. Exceptions check URL name, POST method and known target class or function: `logout` (`CustomLogoutView.post`, session termination including quick exit), `admin:logout` (`AdminSite.logout`, admin logout) and `core:client_rename_warning` (`ClientRenameWarningView.post`, read-only warning). Login, password and recovery forms share mutation budgets. Both passkey begin paths use 60/h before parsing (registration per user, authentication per user or IP). Configuration POSTs and password changes use 60/h per user; admin routes use 60/h per URL and user or IP and admin login 5/min per IP plus 10/h per normalized username across mutations. Caddy has no edge rate limit: resource consumption before application checks remains possible. Undetected cases include custom auth-mixin check hooks (`LoginRequiredMixin`, `PermissionRequiredMixin`, `UserPassesTestMixin`) before throttling and dispatches replaced via `as_view(...)` under the URL name `logout`; the class exception does not prove the dispatch actually executed there. The guard checks imported bindings and configured limits, not load capacity, GET-write semantics or later binding changes. Installed Django-admin/Unfold templates are included in markup guards with specific justified exceptions; the CSRF guard also covers package Python. The inline/Alpine guard scans project templates only.
